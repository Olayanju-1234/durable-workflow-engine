Documentation

Everything you need to run the engine, write durable workflows, and integrate with it from your own services.

Pre-alpha. All 17 weeks of the roadmap are complete: durability, replay, retries, leases, observability, opt-in Raft replication and a public Go SDK are implemented and tested. It has not carried real production traffic yet and the API may still move. Don't run payroll on it.

Introduction

workflowd is a durable workflow execution engine: you write ordinary functions in Go, TypeScript or Python, and the engine guarantees they run to completion even if a process is killed halfway through. It is a lightweight, self-hostable alternative to Temporal — a single binary with no external database.

A workflow is a good fit when your business process:

  • spans multiple steps that each might fail (charge, ship, notify),
  • needs to wait — minutes, days, or for a human approval,
  • must never half-execute (charged but never shipped),
  • needs an audit trail of exactly what happened.

Quickstart

Requires Go 1.26+. No database, no broker, no container runtime. From a fresh clone with empty Go caches this took 42 seconds on a laptop, most of it the first build.

1. Run the engine

git clone https://github.com/Olayanju-1234/durable-workflow-engine.git
cd durable-workflow-engine
go run ./cmd/workflowd --serve

That single process exposes three things, and keeps histories in ./data:

AddressProtocolPurpose
:7233gRPCWorkflow API, used by the Go client and worker
:8233HTTPDashboard + JSON API
:9090HTTP/metrics for Prometheus

2. Run a workflow

In a second terminal:

go run ./examples/hello Ada
started workflow Greeting-3f9c2a7d1e5b8a40
result: Hello, Ada! 👋

That program is a worker (it runs the Greeting workflow and its activities in its own process) and a client (it starts the workflow and waits for the result).

3. Open the dashboard

Visit http://localhost:8233 to see the run: two activities and a durable one-second timer. The dashboard is compiled into the binary.

4. Prove it's durable

Start a drip that sleeps between emails, then stop the engine with Ctrl-C while it sleeps and start it again: 

go run ./examples/onboarding -day 10s ada@example.com

The engine re-reads its histories and re-arms the timer against the recorded deadline, the worker reconnects and registers again, and the next email goes out on time. No email is sent twice. The same guarantee is pinned by tests in the repo, including one that SIGKILLs a real engine process at step 3 of 5 (kill_test.go). The examples/checkout program shows a Saga with a manager-approval signal.

Mental model

Everything rests on one idea: a workflow is an append-only list of events. The engine never stores "current state" anywhere — it derives state by replaying events. 

read history → replay to find current position
             → schedule next step → record result → repeat

Because state is a pure function of the log, crash recovery is not a special code path. Restarting is just running the loop again.

TermMeaning
WorkflowYour orchestration function. Deterministic, no I/O. Runs on the engine.
ActivityOne unit of real work (charge a card, send an email). Runs on a worker. May fail and be retried.
StepOne entry in a workflow's history: an activity, a timer, or a signal wait.
HistoryThe append-only event log for one workflow execution. The only source of truth.
WorkerA separate process that polls for activity tasks over gRPC and reports results.
LeaseA time-boxed claim a worker holds on a dispatched task.

History & durability

Each workflow execution gets its own file: <data-dir>/<workflow-id>.history. Records are appended one at a time and fsync'd before the write is acknowledged, so a "recorded" event has genuinely reached the disk. 

┌───────────┬──────────────┬────────────────────────────┐
│ 4B length │ 4B CRC32C    │ N-byte protobuf HistoryEvent │
└───────────┴──────────────┴────────────────────────────┘
  • Length prefix — lets records be read back sequentially.
  • CRC32C — detects bit rot and torn writes.
  • Torn tail — a partial record from a crash mid-append is truncated on the next open, so the log always resumes on a clean boundary. A checksum failure in the middle of a log is a hard error, never silently skipped.
  • Directory fsync — a new workflow's file is fsync'd into its parent directory, so the file itself can't vanish in a power loss.

Event types recorded today:

  • WorkflowStarted, WorkflowCompleted, WorkflowFailed
  • StepScheduled, StepCompleted, StepFailed
  • TimerStarted, TimerFired, SignalReceived

Replay

To decide what a workflow should do next, the engine re-runs your workflow function from the top. Each durable call it makes is matched against history:

  • Step already completed → the call returns the recorded result instantly. The real work is not repeated.
  • Step still in flight → the function is suspended; the engine waits.
  • Step not in history → this is the next action. The engine records it and dispatches it.

So your function runs many times, but each side effect happens exactly once. This is why workflow code must be deterministic — replay must take the same path every time.

Determinism rules

Breaking these makes a workflow diverge from its recorded history. The engine detects step-level divergence and refuses to proceed rather than corrupting the run.
Don'tDoWhy
time.Now()ctx.Now() (the time of the latest recorded event, in UTC)Wall clock differs on every replay
time.Sleepctx.Sleep(...)Only a recorded timer survives a restart
rand, uuid.New()ctx.SideEffect(...), or generate inside an activityNew value each replay
HTTP calls, DB queries, file I/Octx.ExecuteActivity(...)Side effects would repeat on every replay
go func(){}, channelsctx.ExecuteActivityAsync, ctx.WaitAny (Parallel steps)Goroutine scheduling is non-deterministic
Reading global mutable statePass data through the workflow input and step outputsProcess memory is gone after a restart
Reordering or renaming steps in a running deploymentctx.GetVersion(...)In-flight histories won't match the new code

Also avoid defer with side effects inside workflow functions: the deferred call runs on every replay pass. Recovering panics is harmless; it cannot intercept the engine's suspension of your function. The test environment replays every decision, so a test catches most violations before a deploy does.

Steps: activity, timer, signal

Four kinds of step, all recorded in the same history:

KindCreated byCompleted by
ACTIVITYctx.ExecuteActivityA worker reporting a result over gRPC
TIMERctx.SleepThe engine's timer service when the deadline passes
SIGNALctx.WaitForSignalAn external SignalWorkflow call
MARKERctx.GetVersion, ctx.SideEffectItself: a recorded value, complete as soon as it is written

A timer's absolute deadline is written to disk, so a sleep of 24 hours survives any number of restarts — on recovery the timer is re-armed against the recorded deadline (and fires immediately if it already elapsed while the engine was down).

Writing workflows

A workflow is a Go function of type workflow.Func. It interacts with the outside world only through the workflow.Context it is given. 

go get github.com/olayanju-1234/durable-workflow-engine

The Context API

type Context interface {
	// Run a named activity on a worker and wait for its result.
	// A failed activity returns an error you can handle or propagate.
	ExecuteActivity(name string, input []byte) ([]byte, error)

	// Pause durably for d. Survives restarts.
	Sleep(name string, d time.Duration)

	// Block until a matching external signal arrives; returns its payload.
	// A signal that arrived earlier is buffered and returned immediately.
	WaitForSignal(name, signal string) []byte

	Input() []byte        // the start input
	Now() time.Time       // deterministic clock: latest recorded event, UTC
	Info() Info           // workflow id and type
	Logger() *slog.Logger // drops records while replaying

	// Change code safely while executions are in flight (see Versioning).
	GetVersion(changeID string, minSupported, maxSupported Version) Version
	// Run fn once, record its result, return the recording on every replay.
	SideEffect(name string, fn func() []byte) []byte
}

A complete example

func Checkout(ctx workflow.Context, input []byte) ([]byte, error) {
	// 1. Reserve stock. If this fails, the workflow fails: nothing to undo.
	if _, err := ctx.ExecuteActivity("reserve-stock", input); err != nil {
		return nil, err
	}

	// 2. Wait for a manager to approve. Could be seconds or days.
	if string(ctx.WaitForSignal("manager-approval", "approval")) != "approve" {
		ctx.ExecuteActivity("release-stock", input)
		return nil, errors.New("order rejected by a manager")
	}

	// 3. Charge. If it fails, compensate and fail.
	receipt, err := ctx.ExecuteActivity("charge-card", input)
	if err != nil {
		ctx.ExecuteActivity("release-stock", input)
		return nil, fmt.Errorf("payment failed, stock released: %w", err)
	}
	return ctx.ExecuteActivity("ship-order", receipt)
}

Payloads are bytes. For structured data, marshal JSON (as examples/checkout does with its Order struct).

Step names matter. Each call's name is recorded in history and checked on replay. Names must be stable and unique within a workflow: they are how the engine lines your code up against the durable record.

Workers & clients

A worker runs your workflows and activities in your own process. It registers the workflow types with the engine, polls for decisions and activity tasks over gRPC, and keeps no state of its own, so you can run several and restart them freely. A client starts, signals, terminates and inspects workflows. 

c, err := client.Dial(client.Options{Addrs: []string{"localhost:7233"}})
if err != nil {
	return err
}
defer c.Close()

w := worker.New(c, worker.Options{})
w.RegisterWorkflow("Checkout", Checkout)
w.RegisterActivity("reserve-stock", reserveStock)
w.RegisterActivity("release-stock", releaseStock)
w.RegisterActivity("charge-card", chargeCard)
w.RegisterActivity("ship-order", shipOrder)
if err := w.Start(ctx); err != nil { // returns once the engine knows the types
	return err
}
defer w.Stop()

id, err := c.StartWorkflow(ctx, "Checkout", order, client.WithWorkflowID("order-7"))
err = c.SignalWorkflow(ctx, id, "approval", []byte("approve"))
desc, err := c.DescribeWorkflow(ctx, id) // status, steps, attempts, errors
out, err := c.WaitForResult(ctx, id)     // blocks until it finishes

Errors match sentinels with errors.Is: client.ErrNotFound, ErrAlreadyExists, ErrNotRunning, ErrInvalid, ErrUnavailable, and ErrWorkflowFailed from WaitForResult. w.Run(ctx) is the blocking alternative to Start/Stop and keeps retrying while the engine is down.

Against a cluster, put every node in Addrs. Calls follow the leader hints followers return, and the worker registers its types again whenever the engine it talks to changes.

Activities

An activity is a worker.ActivityFunc: func(ctx context.Context, input []byte) ([]byte, error). It can do anything: HTTP calls, database writes, emails. Its result is recorded once, and a returned error is what the workflow sees (after any engine-side retries). 

func chargeCard(ctx context.Context, input []byte) ([]byte, error) {
	info, _ := worker.GetActivityInfo(ctx)
	key := fmt.Sprintf("%s/%d", info.WorkflowID, info.Sequence) // stable per step
	return payments.Charge(ctx, input, key)                     // idempotent on key
}

Activities run at least once: a worker can die after doing the work but before reporting it, and the step then runs again. Use the workflow id and step sequence as an idempotency key, as above.

Long-running activities

Every dispatched task carries a lease (30 seconds by default). The worker heartbeats every third of the lease while your activity runs, so long activities keep their task. If a heartbeat is rejected the lease is gone (the task was given to another worker), and the activity's ctx is cancelled.

Other languages can execute activities too: anything that speaks proto/service.proto (PollTask, CompleteTask, Heartbeat) or the HTTP protocol is a worker.

Retries & Saga compensation

Retries are handled by the engine and are invisible to your workflow. Set a policy on the call itself: 

receipt, err := ctx.ExecuteActivity("charge", order, workflow.WithRetryPolicy(workflow.RetryPolicy{
	MaxAttempts:    3,                      // counts the first try; 1 = no retry
	InitialBackoff: 200 * time.Millisecond, // doubles each attempt
	MaxBackoff:     5 * time.Second,        // ceiling
}))

TypeScript: ctx.activity('charge', order, { retry: { maxAttempts: 3, initialBackoffMs: 200 } }); Python: ctx.activity("charge", order, retry=RetryPolicy(max_attempts=3, initial_backoff=0.2)). The policy is recorded with the step, so the retries continue after a restart or a leader change. An engine can also set a default per step name (Engine.SetRetryPolicy, used by the demo); a policy on the call wins.

The default is no retry (MaxAttempts: 1) — a failure surfaces to the workflow immediately. Retries reuse the same step sequence, so a retried activity stays one logical step with an attempts count (visible in the dashboard). Backoffs are durable: if the engine restarts during one, the retry is re-armed.

Saga compensation needs no special machinery. Once retries are exhausted, the activity error is returned to your Go code, so "undo" is just an ordinary error branch that calls more activities, as in the release-stock calls in the example above.

Parallel steps

Start several steps before waiting on any of them. Every step still gets its own place in history, and the engine dispatches them at once: 

stock := ctx.ExecuteActivityAsync("check-stock", order)
price := ctx.ExecuteActivityAsync("quote-price", order)
if _, err := stock.Get(); err != nil { ... }
quote, err := price.Get()

// A race: whichever finishes first.
reply := ctx.WaitForSignalAsync("reply", "approved")
deadline := ctx.NewTimer("deadline", 48*time.Hour)
if ctx.WaitAny(reply, deadline) == 1 {
	return nil, errors.New("no reply in time")
}

WaitAny picks the step whose result history recorded first, not the first in your argument list, so every replay makes the same choice. There is deliberately no non-blocking "is it done yet?": its answer would depend on when a replay runs. A step the engine is retrying has no result yet, so your code keeps waiting on it. A workflow may return while steps are still running; they are abandoned.

TypeScript: start calls without awaiting them and use Promise.all, and ctx.waitAny([...]) instead of Promise.race (which picks by call order). Python: ctx.activity_async, ctx.sleep_async, ctx.wait_for_signal_async, then ctx.wait_all / ctx.wait_any.

Schedules

A schedule starts a workflow every time a cron expression fires: 

err := c.CreateSchedule(ctx, client.Schedule{
	ID:            "nightly-report",
	Cron:          "0 2 * * MON-FRI", // or @hourly, @daily, "@every 15m"
	Timezone:      "Europe/London",   // empty is UTC
	WorkflowType:  "Report",
	SkipIfRunning: true,              // skip a fire while the last run is still going
})

Over HTTP: POST /api/schedules, GET /api/schedules, DELETE /api/schedules/{id}. Schedules are durable and, in a cluster, fire on the leader only. Each run's workflow id is <schedule id>-<fire time> (e.g. nightly-report-20261022T010000Z), so a fire is never started twice, even across a restart or a failover. After downtime, the latest fire missed in the last 24 hours runs once. Fields: minute, hour, day of month, month, day of week, with *, ranges, steps, lists and names; when both day fields are set, either matches.

Testing workflows

Package testsuite runs a workflow inside a unit test: no server, activities you supply (real or mocked), and virtual time, so a workflow that sleeps for a week finishes in milliseconds. 

func TestRejectedOrderReleasesStock(t *testing.T) {
	env := testsuite.NewEnv()
	env.RegisterActivity("reserve-stock", reserveStock)
	env.RegisterActivity("release-stock", releaseStock)
	env.SignalAfter(7*24*time.Hour, "approval", []byte("reject"))

	_, err := env.ExecuteWorkflow(Checkout, order)
	if !errors.Is(err, testsuite.ErrWorkflowFailed) {
		t.Fatalf("got %v", err)
	}
	// env.Elapsed() == 168h of virtual time; the test took milliseconds.
}
  • Timers skip ahead in virtual time; ctx.Now() follows the virtual clock.
  • Signals are scheduled in virtual time and buffered exactly as the engine buffers them.
  • A wait on a signal nobody will send returns testsuite.ErrBlocked instead of hanging.
  • History is recorded as the engine records it and replayed for every decision, so non-deterministic code fails the test.
  • Engine-side retry policies are not simulated: a failed activity returns its error at once.

Changing running code

Workflows can run for weeks, so you will change code while executions are in flight. Adding, removing or reordering steps would make those executions' histories disagree with the new code. Wrap the change in GetVersion: 

if ctx.GetVersion("fraud-check", workflow.DefaultVersion, 1) == 1 {
	ctx.ExecuteActivity("fraud-check", order)
}
  • An execution reaching this point for the first time records version 1 as a MARKER step and takes the new branch on every replay.
  • An execution that ran past this point before the deploy has no marker there, gets workflow.DefaultVersion, and replays the old branch.
  • Once no execution can still need the old branch, raise minSupported and delete the branch, but keep the call. An execution whose recorded version is out of range fails as non-deterministic instead of silently taking the wrong path.
Rollback caveat. Binaries built before version markers existed cannot read a history that contains one. Roll back only after such workflows have finished and been deleted.

Embedding the engine

For a single service that wants durable workflows without running another process, or for integration tests, embedded runs the real engine inside your program on a local data directory: 

srv, err := embedded.Start(embedded.Options{DataDir: "data"})
if err != nil {
	return err
}
defer srv.Close()

w := worker.New(srv.Client(), worker.Options{})
// ...register, then w.Start(ctx), then srv.Client().StartWorkflow(...)

Histories are fsync'd to DataDir and survive a restart of your process; workers and clients use exactly the same code paths as against a remote engine. The data directory must not be shared with another engine, and cluster mode is not embeddable.

Polyglot workflows

Workflow code does not have to be Go. The engine owns durability — history, replay position, timers, retries, leases — while an SDK in your language owns the orchestration logic. They talk over a small protocol.

SDKLocationStatus
Goworkflow/, worker/, client/Tested end to end, including leader failover (gRPC; see Workers & clients)
TypeScript / Nodesdks/typescript/Run end to end in CI on every change, in plaintext and over TLS with a token. Packaged for npm, not yet published
Pythonsdks/python/Run end to end in CI, as above. Packaged for PyPI, not yet published
Javasdks/java/Compiled for Java 11 and run end to end in CI, as above. Packaged for Maven Central, not yet published

Every non-Go SDK is dependency-free: Node's fetch, Python's urllib and Java's HttpClient are all built in. No npm install, no pip install, no protobuf toolchain.

Activities were already language-agnostic. Any process that speaks the API can execute activities — that has been true since Week 3. What the SDKs add is running the workflow function itself outside the engine.

TypeScript

import { Worker, WorkflowFailure } from './workflowd.mjs';

const worker = new Worker({ address: 'http://localhost:8233' });

worker.workflow('OrderWorkflow', async (ctx) => {
  const reserved = await ctx.activity('reserve', ctx.input);

  await ctx.sleep('settle', 2000);                    // durable
  const ok = await ctx.waitForSignal('gate', 'approved');
  if (ok !== 'yes') throw new WorkflowFailure('rejected');

  try {
    await ctx.activity('charge', reserved);
  } catch (err) {
    await ctx.activity('release', reserved);          // compensate
    throw new WorkflowFailure(`charge failed: ${err.message}`);
  }
  return await ctx.activity('ship', reserved);
});

worker.activity('reserve', async (input) => `reserved:${input}`);
await worker.run();

Run it with node example.mjs — no install step.

Python

from workflowd import Worker, WorkflowFailure, ActivityFailure

worker = Worker(address="http://localhost:8233")

@worker.workflow("OrderWorkflow")
def order(ctx):
    reserved = ctx.activity("reserve", ctx.input)

    ctx.sleep("settle", 2.0)                          # durable
    if ctx.wait_for_signal("gate", "approved") != "yes":
        raise WorkflowFailure("rejected")

    try:
        ctx.activity("charge", reserved)
    except ActivityFailure as err:
        ctx.activity("release", reserved)             # compensate
        raise WorkflowFailure(f"charge failed: {err}")
    return ctx.activity("ship", reserved)

@worker.activity("reserve")
def reserve(payload):
    return f"reserved:{payload}"

worker.run()

The SDK protocol

Five HTTP endpoints. If your language isn't listed above, this is everything you need to add it — a complete SDK is about 250 lines. 

POST /api/workflow-types            {"workflow_types":["OrderWorkflow"],"worker_id":"w1"}
GET  /api/workflow-tasks?types=OrderWorkflow    (long-poll; 204 = nothing yet)
POST /api/workflow-tasks/complete   {"workflow_id":...,"task_token":...,"command":{...}}
GET  /api/activity-tasks?activities=reserve,charge   (long-poll; 204 = nothing yet)
POST /api/activity-tasks/complete   {"workflow_id":...,"step_name":...,"sequence":...,"lease_token":...,"output":...,"error":...}

Always pass types and activities: a poll without a filter receives any task, including ones only another worker can run. Workers that register the same activity name share its queue, so they must implement it the same way.

A workflow task carries the already-reconstructed state — input, steps in order with their results, and buffered signals — so your SDK never has to implement the history fold: 

{
  "workflow_id": "order-42",
  "workflow_type": "OrderWorkflow",
  "task_token": "9f3c...",
  "history_length": 4,
  "input": "order-42",
  "steps": [
    {"step_name":"reserve","sequence":1,"kind":"ACTIVITY","status":"COMPLETED","output":"reserved:order-42"},
    {"step_name":"charge","sequence":2,"kind":"ACTIVITY","status":"SCHEDULED","attempts":2}
  ],
  "signals": [{"name":"approved","payload":"yes"}]
}

Replay your workflow function against steps in call order, then return the commands it issued before it blocked: one in "command", several in "commands": [...] (parallel steps, with consecutive sequences):

{"type":"schedule_activity","step_name":"charge","sequence":2,"input":"...",
 "retry_policy":{"max_attempts":3,"initial_backoff_ms":500}}
{"type":"start_timer","step_name":"wait","sequence":3,"delay_ms":60000}
{"type":"await_signal","step_name":"gate","sequence":4,"signal_name":"approved"}
{"type":"record_marker","step_name":"fraud-check","sequence":5,"marker":"version","data":"1"}
{"type":"complete_workflow","output":"..."}
{"type":"fail_workflow","error":"..."}
{"type":"noop"}

Binary payloads travel as a <field>_base64 twin; resolved steps carry resolved_event_id for "first of" races. The full protocol is in sdks/README.md.

How replay suspends — the one hard part

When replay reaches a step with no recorded result, your workflow function must stop without workflow code being able to intercept it. This matters more than it sounds, because workflows legitimately write try { await activity() } catch { compensate() }. If your suspend signal is an ordinary exception, that catch swallows it and compensation runs on every replay pass.

LanguageMechanismWhy it's safe
Goruntime.Goexit on the workflow's own goroutinerecover() cannot stop it, so workflow code that recovers panics can't swallow a suspension
Pythonsubclass BaseExceptionexcept Exception doesn't catch it
Javasubclass Errorcatch (Exception) doesn't catch it
TypeScripta promise that never settlescatch catches everything in JS, so suspension must not be a throw at all
The TypeScript case is not hypothetical: the first version of that SDK used a thrown sentinel, and a workflow with a try/catch around an activity silently stalled. It now suspends with a non-settling promise, which workflow code cannot observe.

Safety properties you get for free

  • SDK workers are stateless. Every task carries everything needed to replay, so a crashed SDK worker costs nothing — the task is re-dispatched.
  • Stale decisions are fenced. Each task records the history length it was based on. If history moved on while your worker was thinking, the command is rejected with 409 — poll again. This is what makes re-dispatch safe: two workers may both decide, but only one command can ever apply.
  • Malformed commands can't corrupt a workflow. The engine validates step sequencing before anything reaches the log, and a rejected command leaves the task pending so a fixed deployment heals the workflow automatically.
  • Replay errors fail loudly. If your SDK reports that it can't replay a history (the code changed incompatibly), the workflow fails with that message rather than spinning forever.

Auth & TLS

Each piece is opt-in and independent, so a deployment that sets none of them behaves exactly as before.

PortTLSAuth

Dashboard + JSON API (--http-addr)--tls-cert/--tls-keyThe API token on every /api route but /api/health; reads can be left open with --auth-public-reads

Keep secrets out of the command line and the unit file: a token file (mode 600; the daemon warns if others can read it) or an environment variable from a root-only EnvironmentFile.

openssl rand -hex 32 > /etc/workflowd/token && chmod 600 /etc/workflowd/token
workflowd --serve --auth-token-file /etc/workflowd/token \
  --tls-cert /etc/workflowd/tls.crt --tls-key /etc/workflowd/tls.key

Clients send the same token. The dashboard asks for it once per tab when the API answers 401. In a cluster, followers redirect clients to the leader by the host in its --peers entry, so each node's --tls-cert must be valid for that host as well as any name clients dial.

c, err := client.Dial(client.Options{
    Addrs:     []string{"workflowd.internal:7233"},
    TLS:       &tls.Config{},                       // or RootCAs: your CA pool

What this does not give you yet: there is one shared API token, so no per-user identities or roles; client certificates are only checked on the Raft port; and any certificate the cluster CA signed can speak for any member, so give the Raft CA to cluster nodes only.

Crash recovery

On startup (before serving traffic) the engine scans the data directory and, for each workflow:

  • Terminal or not started — nothing to do.
  • Waiting on an activity — the task is re-queued for a worker.
  • Waiting on a timer — re-armed against the recorded deadline (fires immediately if it already passed).
  • Waiting on a signal — any signal buffered before the crash is delivered.
  • Mid-decision — the decision loop advances one step.
  • Failed with retries remaining — the backoff timer is re-armed.
At-least-once, not exactly-once. If a worker finished an activity but died before reporting the result, that activity runs again after recovery. Make your activities idempotent — use the workflow id plus step name as an idempotency key.

Leases & dead workers

When a task is dispatched, the worker receives a random lease token and a deadline (30s by default). CompleteTask and Heartbeat must present that token.

  • Miss the deadline and the engine records StepFailed("lease expired"), then feeds it to the normal retry machinery — attempts remaining means backoff and reassign; exhausted means the workflow sees the error and can compensate.
  • A "zombie" worker that comes back late has a stale token and is rejected, so two workers can never both record a result for the same attempt.
  • Because a dead worker counts as a failed attempt, a task that kills every worker it touches can't loop forever.

With the default no-retry policy, one dead worker fails the workflow explicitly. Set MaxAttempts > 1 on activities that should tolerate worker crashes.

Running a cluster

Give each node the same --peers list and its own --node-id and data directory, and three (or five) workflowd processes form a Raft cluster: 

workflowd --serve --node-id n1 --peers n1=10.0.0.1:7333,n2=10.0.0.2:7333,n3=10.0.0.3:7333 \
  --data-dir /var/lib/workflowd --addr :7233 --http-addr :8233
  • Every history event is written to a majority of nodes before it counts, and every node keeps a full copy of every workflow's history.
  • Only the leader runs the engine (task queue, timers, leases, the demo worker, retention). Followers answer workflow calls with HTTP 503 or gRPC Unavailable, naming the leader (X-Workflowd-Leader header, JSON body, or workflowd-leader* trailers). /api/health works on every node.
  • If the leader dies, another node takes over within one to two election timeouts and resumes every workflow from the replicated history, exactly as a restarted single node would.
  • A cluster survives losing any minority of nodes (one of three, two of five).
  • The Go client and worker follow leader hints: give client.Options.Addrs every node.
Still at-least-once. An activity can run twice across a failover, and a write that was in flight during a leader change can return an error even though it succeeded. Retry with the same workflow_id: a duplicate start returns AlreadyExists.

Limitations

Known and deliberate, as of the end of the 17-week roadmap:

  • Clustering is young. Membership is fixed by --peers; the Raft port is plaintext unless you set --raft-tls-*; every history write is a Raft commit on the leader, so a cluster adds availability, not write throughput; and a single-node data directory can't be moved into a cluster. A single node's data directory is its single point of failure; back it up.
  • Auth is one shared token. TLS and the token are opt-in and cover every port (Auth & TLS), but there are no per-user identities or roles, and with nothing set every port is open plaintext.
  • At-least-once activity execution: make activities idempotent. (Signals are exactly-once; each carries an idempotency key.)
  • Parallel steps are Go, TypeScript and Python; the Java SDK runs one step at a time.
  • Not load-tested. Workflows run in parallel, each under its own lock with its state cached, and listing reads an in-memory index; the main remaining cost is one fsync per event (ADR-0006).
  • Rollback: binaries from before parallel steps can't read a history that ran some.

FAQ

How is this different from a job queue?

A queue remembers tasks; this remembers your program's position. With a queue, a crash between "charge succeeded" and "enqueue ship" loses the thread of the process. Here that transition is an event in a durable log, so restarting resumes exactly at the next step.

Do I need a database?

No. The data directory is the database. Each workflow is one append-only file.

What happens if I redeploy while workflows are running?

Workflows resume from history. That is safe as long as the step sequence your code produces hasn't changed for executions already in flight. Wrap changes in GetVersion; an unguarded change is detected as non-determinism and the affected executions fail rather than take a wrong path.

How many workers should I run?

Watch workflowd_task_queue_depth. If it grows, add workers. Workers are stateless, so scaling is just running more processes pointed at the same engine.

Can I use it from another language?

Yes — both halves. Activities have always been language-agnostic (any process that speaks the API can execute them). Workflow definitions can now also run outside the engine: TypeScript, Python and Java SDKs ship in sdks/, each run end to end in CI, and the protocol is three HTTP endpoints if you want to add another language.

What is the license?

Apache-2.0. The engine is open source and stays that way; a managed/hosted product is the intended commercial layer.
